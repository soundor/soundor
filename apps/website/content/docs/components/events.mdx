The [node components](/docs/components) take event props: `onPointerDown`,
`onClick`, `onDoubleClick`, `onKeyDown`, `onWheel`, `onFocus` and the others
below. `onPointerDown`, `onPointerMove`, `onPointerUp`, `onClick`,
`onDoubleClick`, `onContextMenu`, `onWheel` and `onKeyDown` also have
`…Capture` variants. They receive
`soundor:ui`'s Web-style events, which capture and bubble through the view's
nodes as in the DOM. `Portal`, `Modal` and `FocusScope` take their own props;
put node event handlers on the content they render.

```tsx
<View
  focusable
  onPointerDown={(event) => startDrag(event.pageY)}
  onWheel={(event) => nudge(-event.deltaY)}
  onKeyDown={(event) => {
    if (event.key === 'ArrowUp') {
      nudge(1);
      event.preventDefault();
    }
  }}
/>
```

- **Capture and bubble:** an event goes down to its target through the
  `…Capture` props, then back up through the others. Enter, leave, focus,
  blur and focus-visible changes do not bubble.
- **`preventDefault()`** stops the runtime's own response: a press focusing a
  node, a text input's editing, a key or wheel input going on to the plugin's
  host (a DAW's shortcuts).
- **`stopPropagation()`** keeps other nodes from seeing the event;
  `stopImmediatePropagation()` keeps the target's other listeners from seeing
  it too.
- **Pointer capture** is implicit: from a press to its release, the pressed
  node receives the moves, wherever the pointer goes. It starts before the
  `pointerdown` listeners run, so they can lock the press
  ([Pointer lock](#pointer-lock)).
- **`movementX`/`movementY`** say how far the pointer moved since its previous
  event, so a drag needs no starting point.
- **`screenX`/`screenY`** are where the pointer is on the screen, in the
  editor's logical pixels: they do not move when the editor resizes or, an
  editor that scales, zooms, as `clientX`/`clientY` do. A drag that resizes
  the editor measures with them
  ([A resize grip](/docs/api/ui#a-resize-grip)). A wheel event's are its
  `clientX`/`clientY`.
- **The wheel with Control is a zoom**, as browsers take it, and a trackpad's
  pinch arrives in a browser as one (`ctrlKey`, the zoom in `deltaY`). It never
  scrolls a scroll view. Unless a listener calls `preventDefault()`, it goes on
  to the host, which in a browser zooms the page. To zoom something of your
  own, a waveform say, handle `onWheel` when `event.ctrlKey` is set and call
  `preventDefault()`.
- **Focus:** a press focuses the nearest `focusable` node, unless its
  `pointerdown` is prevented; Tab and Shift+Tab move through focusable nodes.
  Keys go to the focused node. Show focus with `focusVisible`, not `focused`
  ([Focus rings](#focus-rings)).
- **`onContextMenu`** fires when the secondary button goes down, so a UI can
  open its own menu ([Portal](/docs/components/portal#over-everything)).
- **Double clicks** are the platform's: `onDoubleClick` fires right after
  the second click's `onClick` ([Double clicks](#double-clicks)).

## Double clicks

<Snippet name="double-click" height={180} />

The platform decides which clicks make a series: those close enough in time
(its double-click time, which the user sets) and in place, of the same
button. Every `click` says which of a series it is in `event.detail`: 1 for
a single click, 2 for the second of a double click, 3 for a triple click.
The second is followed at once by a `dblclick`, also with `detail` 2, on
the same node:

```tsx
<View
  onDoubleClick={() => setValue(DEFAULT)}
  onClick={(event) => {
    if (event.detail === 1) select();
  }}
/>
```

- **A double click is two clicks first:** `onClick` runs for both, so code
  that should not run for a double click's first click (opening something,
  say) has to wait, or be harmless when undone by the double click.
- **The same node:** `dblclick` goes where the second click went, the
  deepest node holding both its press and its release.
- **Other events have no count:** `detail` is 0 for `pointerdown`,
  `pointerup` and the rest.
- **The platform's time:** the JUCE runtime reads macOS's and Windows'
  setting, and on Linux the desktop's (`Net/DoubleClickTime`, as GNOME and
  KDE publish it), else 400 ms; in a browser it is the browser's count.
- **In tests** there is no time: [`user.dblClick`](/docs/testing/dbl-click)
  and Soundor Driver's [`dblclick()`](/docs/driver/interacting) say which
  click of a series each one is.

## Focus rings

A press focuses what it presses, so a ring drawn while a node is `focused`
appears on every click. As CSS's `:focus-visible`, `node.focusVisible` says
whether the focus should show: not when a press gave it, until a key is
pressed (not a shortcut nor a modifier on its own); when Tab, a screen
reader or code moved it after a key; and always in a text input.
`onFocusVisibleChange` fires whenever it changes, with
`event.focusVisible`, and a [`Pressable`](/docs/components/pressable)'s
state has it. Draw the ring with an
[outline](/docs/components/style#outline), which takes no room, so nothing
moves when it shows:

```tsx
const [ring, setRing] = useState(false);

<View
  focusable
  onFocusVisibleChange={(event) => setRing(event.focusVisible)}
  style={{
    borderRadius: 42,
    outlineWidth: ring ? 2 : 0,
    outlineOffset: 2,
    outlineColor: '#9473ca',
  }}
/>;
```

Both runtimes decide it by these rules, the web runtime too, rather than
by the browser's own.

## Coordinates

Layout and view-relative positions use the view's logical pixels. Screen
positions use the editor's logical pixels:

| Space   | Relative to                          | Where                                                        |
| ------- | ------------------------------------ | ------------------------------------------------------------ |
| Local   | The event's target                   | `event.locationX`, `event.locationY`                         |
| Parent  | The parent's box (scrolling aside)   | `node.layout`                                                |
| Surface | The plugin view's top-left corner    | `event.pageX`, `event.pageY`, `node.getBoundingClientRect()` |
| Screen  | The screen, in editor logical pixels | `event.screenX`, `event.screenY`                             |

`getBoundingClientRect()` is where the node shows, after its ancestors have
scrolled. Device pixels (a Retina scale, a host that zooms
the view) are the renderer's business and never show up in these numbers.
Screen positions remain stable as the editor resizes or zooms: use their
deltas for an editor resize grip. A wheel event falls back to `clientX`/`clientY`.
(`clientX`/`clientY` and `offsetX`/`offsetY` are the Web names for
`pageX`/`pageY` and `locationX`/`locationY`.)

## Pointer lock

<Snippet name="pointer-lock" height={180} />

A knob or a fader can lock the pointer while it is dragged:
`event.currentTarget.requestPointerLock()` in `onPointerDown`. While locked,
the pointer is hidden and the screen's edges don't stop it; the events keep
going to the node that locked it, their positions stay where the lock began,
and `movementX`/`movementY` say how far it moved. The lock ends with the
release, or `exitPointerLock()` from `soundor:ui`, and the pointer shows
again where it began, on the knob.

```tsx
import { View } from '@soundor/react';
import { useRef } from 'react';

function Knob({
  value,
  onChange,
}: {
  value: number;
  onChange(v: number): void;
}) {
  const dragging = useRef(false);
  return (
    <View
      style={{ cursor: 'ns-resize' }}
      onPointerDown={(event) => {
        dragging.current = true;
        event.currentTarget?.requestPointerLock().catch(() => {});
      }}
      onPointerMove={(event) => {
        if (dragging.current) onChange(value - event.movementY / 200);
      }}
      onPointerUp={() => (dragging.current = false)}
      onPointerCancel={() => (dragging.current = false)}
    />
  );
}
```

- **Only for a press:** a lock needs a mouse or pen pressing the node (or a
  node in it), which is why it is asked for in `onPointerDown`. Otherwise
  `requestPointerLock()` rejects with a `NotAllowedError`; touches are never
  locked.
- **Keep your own drag state,** as above: `movementY` works without the lock
  too, so a knob still turns if the lock is refused, stopping at the screen's
  edge.
- **`pointerLockNode()`** is the node holding the lock, or `null`. The
  release still comes under the lock, which ends after it.
- **In a browser** (the [web runtime](/docs/web-runtime)) the lock is the
  page's Pointer Lock: Escape ends it early, and Firefox says so in a banner.
