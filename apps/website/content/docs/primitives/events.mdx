title: Events
description: The Web-style pointer, wheel, key and focus events node components take, and their coordinates.

The [node components](/docs/primitives) take event props: `onPointerDown`,
`onClick`, `onDoubleClick`, `onKeyDown`, `onWheel`, `onFocus` and the others
below. `onPointerDown`, `onPointerMove`, `onPointerUp`, `onClick`,
`onDoubleClick`, `onContextMenu`, `onLongPress`, `onWheel` and `onKeyDown` also have
`…Capture` variants. They receive
`soundor:ui`'s Web-style events, which capture and bubble through the view's
nodes as in the DOM. `Portal`, `Modal` and `FocusScope` take their own props;
put node event handlers on the content they render.

```tsx
<View
  focusable
  onPointerDown={(event) => startDrag(event.pageY)}
  onWheel={(event) => nudge(-event.deltaY)}
  onKeyDown={(event) => {
    if (event.key === 'ArrowUp') {
      nudge(1);
      event.preventDefault();
    }
  }}
/>
```

- **Capture and bubble:** an event goes down to its target through the
  `…Capture` props, then back up through the others. Enter, leave, focus,
  blur and focus-visible changes do not bubble.
- **`preventDefault()`** stops the runtime's own response: a press focusing a
  node, a text input's editing, a key or wheel input going on to the plugin's
  host (a DAW's shortcuts).
- **`stopPropagation()`** keeps other nodes from seeing the event;
  `stopImmediatePropagation()` keeps the target's other listeners from seeing
  it too.
- **Pointer capture** is implicit: from a press to its release, the pressed
  node receives the moves, wherever the pointer goes. It starts before the
  `pointerdown` listeners run, so they can lock the press
  ([Pointer lock](#pointer-lock)).
- **`movementX`/`movementY`** say how far the pointer moved since its previous
  event, so a drag needs no starting point.
- **`screenX`/`screenY`** are where the pointer is on the screen, in the
  editor's logical pixels: they do not move when the editor resizes or, an
  editor that scales, zooms, as `clientX`/`clientY` do. A drag that resizes
  the editor measures with them
  ([A resize grip](/docs/api/ui#a-resize-grip)). A wheel event's are its
  `clientX`/`clientY`.
- **The wheel with Control is a zoom**, as browsers take it, and a trackpad's
  pinch arrives in a browser as one (`ctrlKey`, the zoom in `deltaY`). It never
  scrolls a scroll view. Unless a listener calls `preventDefault()`, it goes on
  to the host, which in a browser zooms the page. To zoom something of your
  own, a waveform say, handle `onWheel` when `event.ctrlKey` is set and call
  `preventDefault()`.
- **Focus:** a press focuses the nearest `focusable` node, unless its
  `pointerdown` is prevented; Tab and Shift+Tab move through focusable nodes.
  Keys go to the focused node. Show focus with `focusVisible`, not `focused`
  ([Focus rings](#focus-rings)).
- **`key` and `code`:** `key` is what a press types, which depends on the
  layout and the modifiers; `code` is the physical key, as the Web names it
  (`'KeyS'`, `'Digit1'`, `'ShiftLeft'`), whatever it types. Match text and
  named keys (`'Enter'`, `'ArrowUp'`) by `key`, and a shortcut whose
  modifiers change what it types by `code`: Option+S on macOS has the key
  `'ß'` and Shift+1 on a US layout `'!'`, but their codes are `'KeyS'` and
  `'Digit1'` ([Keyboard shortcuts](#keyboard-shortcuts)).
- **`onContextMenu`** is a [request to open a context menu](#context-menus).
- **Double clicks** are the platform's: `onDoubleClick` fires right after
  the second click's `onClick` ([Double clicks](#double-clicks)).

## Context menus

`contextmenu` is a request for a context menu, not a right-click event. The
engine recognizes every way of asking for one on any view: a secondary
click (Control-click on macOS), Shift+F10 or the Context Menu key on the
focused node, a touch [long press](#long-presses), and the
`showContextMenu` [accessibility action](/docs/primitives/accessibility#context-menus).
All of them are the same `contextmenu` event, for `soundor:ui` listeners and
the `onContextMenu` and `onContextMenuCapture` props; the plugin decides
what to show. It works alongside primary interactions such as `onPress`.

```tsx
const handleContextMenu = (event: PointerEvent) => {
  event.preventDefault(); // Suppress the browser's menu for this request.
  openMenu({ x: event.pageX, y: event.pageY });
};

<View
  focusable
  accessibilityLabel="Track options"
  accessibilityActions={[{ name: 'showContextMenu' }]}
  onContextMenu={handleContextMenu}
>
  <Text>Track options</Text>
</View>;

<Pressable onPress={openSettings} onContextMenu={handleContextMenu}>
  <Text>Settings</Text>
</Pressable>;
```

Use `pageX`/`pageY` (the same view-relative logical pixels as
`clientX`/`clientY`) to position a menu in a [portal](/docs/primitives/portal).
For a pointer request, these are the pointer's coordinates. For a keyboard
or accessibility request, they are the bottom-left of the target's bounds;
`pointerType` is `''`, `button` and `pointerId` are `-1`, and no buttons are
held. `offsetX`/`offsetY` are relative to the original target, even when an
ancestor handles the request.

The keyboard shortcuts act on the focused node. A plain view can opt into
keyboard focus with `focusable`. `preventDefault()` on `keydown` cancels the
request. `preventDefault()` on `contextmenu` says the plugin handled it: a
browser does not show its own menu (where its event is cancelable), and in
a plugin's editor the shortcut does not go on to the host. Repeats of a held
shortcut make no new request.

A wrapper can observe requests without advertising an accessibility action:

```tsx
<View onContextMenuCapture={observeRequest}>
  <Application />
</View>
```

A listener never offers a context menu to assistive technology, on its node
or its descendants: declare `showContextMenu` in the `accessibilityActions`
of the element that has one ([Accessibility](/docs/primitives/accessibility#context-menus)).
A secondary click on a node that also handles presses does not press it.

| Runtime | Pointer and keyboard                                                            | Accessibility                                |
| ------- | ------------------------------------------------------------------------------- | -------------------------------------------- |
| macOS   | Secondary click, Control-click, Shift+F10, Context Menu key                     | `AXShowMenu`                                 |
| Linux   | Secondary click, Shift+F10, Context Menu key                                    | AT-SPI action `popup`                        |
| Windows | Secondary click, Shift+F10, Context Menu key                                    | UI Automation `ShowContextMenu`              |
| iOS     | What the host delivers                                                          | VoiceOver action "Show context menu"         |
| Web     | The browser's menu gestures (touch long press too), Shift+F10, Context Menu key | A `contextmenu` the browser sends unprompted |

## Long presses

`longpress` is a gesture event on any view, through `soundor:ui` and the
`onLongPress` and `onLongPressCapture` props. The engine recognizes it: the
primary pointer held 500 ms (a `Pressable`'s `delayLongPress`) without
moving more than 10 logical pixels. Releasing or canceling the pointer,
moving further, scrolling, pointer lock, the node leaving the tree, and
`preventDefault()` on its `pointerdown` (which claims the press) end it
first. `pointerType` says where it came from: `'touch'`, `'mouse'` or
`'pen'`, and `''` for the accessibility `longpress` action.

Its default, for a touch long press only, is a `contextmenu` event at the
same node and point, so `onContextMenu` alone opens a menu on a touch
screen, with no `onLongPress` needed. A mouse long press and the
accessibility `longpress` action (a different request from
`showContextMenu`) have no default. To give a touch hold another meaning,
cancel it; right-click, the keyboard and assistive technology still request
the menu:

```tsx
<View
  onLongPress={(event) => {
    event.preventDefault(); // No contextmenu follows this hold.
    resetValue();
  }}
  onContextMenu={handleContextMenu}
/>
```

## Event order

| Invocation                             | Event sequence                        |
| -------------------------------------- | ------------------------------------- |
| Secondary click or macOS Control-click | `contextmenu`                         |
| Shift+F10 or Context Menu key          | `keydown` → `contextmenu`             |
| Touch long press                       | `longpress` → `contextmenu`           |
| Mouse long press                       | `longpress`                           |
| Accessibility `showContextMenu`        | `accessibilityaction` → `contextmenu` |
| Accessibility `longpress`              | `accessibilityaction` → `longpress`   |

(Unrelated pointer and key events are left out.) Each event captures and
bubbles, and each arrow is a default: it runs after the event before it has
gone through every listener, unless one called `preventDefault()`.
`stopPropagation()` does not cancel it, and neither the presence nor the
absence of a listener changes it.

A long press canceled, or whose `contextmenu` was canceled, is consumed: its
release does not click. An unhandled one still clicks, and a `Pressable`
never presses after its `onLongPress` ran.

Touch long presses need a runtime that receives touch input: the web runtime
does; the VST3 runtime's desktop editors get mouse input (a touch screen's
emulated mouse included), so a held finger there is a mouse long press.
Browsers may keep a gesture for themselves (scrolling, text selection, the
system's menu) before Soundor sees it; where a browser sends no cancelable
`contextmenu`, its own menu cannot be replaced. A shortcut the host or the
system takes before the editor gets it cannot request a menu.

## Keyboard shortcuts

A shortcut handled by `onKeyDown` on a node that holds the focus (the
editor's outermost view, say, made `focusable`) runs while the editor has
the keyboard:

```tsx
<View
  focusable
  accessibilityKeyShortcuts="Control+S Meta+S"
  onKeyDown={(event) => {
    if ((event.ctrlKey || event.metaKey) && event.code === 'KeyS') {
      save();
      announce('Preset saved'); // from soundor:ui
      event.preventDefault();
    }
  }}
/>
```

- **`code` for letters and digits with modifiers**, since what they type
  changes with Alt (Option), Shift and the layout; `key` for named keys.
  `code` names the key where it is on a US keyboard, so on an AZERTY one
  `'KeyQ'` is the key labelled A: match `key` where the label matters more
  than the place.
- **Every runtime gives it:** the browser's on the web; natively the key's
  scan code (Windows), virtual key code (macOS) or keycode (X11). Soundor
  Driver's keys and Testing Library's `user.keyboard` have the US key that
  types them (`'!'` is `'Digit1'`); `fireEvent.keyDown` has the `code` it is
  given, else `''`.
- **`preventDefault()`** keeps the key from the host: unprevented, a DAW
  may take it for its own shortcut.
- **Tell assistive technology** with `accessibilityKeyShortcuts` and, for an
  action that changes nothing focused, `announce()`
  ([Accessibility](/docs/primitives/accessibility#keyboard-shortcuts)).

## Double clicks

<Snippet name="double-click" height={180} />

The platform decides which clicks make a series: those close enough in time
(its double-click time, which the user sets) and in place, of the same
button. Every `click` says which of a series it is in `event.detail`: 1 for
a single click, 2 for the second of a double click, 3 for a triple click.
The second is followed at once by a `dblclick`, also with `detail` 2, on
the same node:

```tsx
<View
  onDoubleClick={() => setValue(DEFAULT)}
  onClick={(event) => {
    if (event.detail === 1) select();
  }}
/>
```

- **A double click is two clicks first:** `onClick` runs for both, so code
  that should not run for a double click's first click (opening something,
  say) has to wait, or be harmless when undone by the double click.
- **The same node:** `dblclick` goes where the second click went, the
  deepest node holding both its press and its release.
- **Other events have no count:** `detail` is 0 for `pointerdown`,
  `pointerup` and the rest.
- **The platform's time:** the VST3 runtime reads macOS's and Windows'
  setting, and on Linux the desktop's (`Net/DoubleClickTime`, as GNOME and
  KDE publish it), else 400 ms; in a browser it is the browser's count.
- **In tests** there is no time: [`user.dblClick`](/docs/testing/dbl-click)
  and Soundor Driver's [`dblclick()`](/docs/driver/interacting) say which
  click of a series each one is.

## Focus rings

A press focuses what it presses, so a ring drawn while a node is `focused`
appears on every click. As CSS's `:focus-visible`, `node.focusVisible` says
whether the focus should show: not when a press gave it, until a key is
pressed (not a shortcut nor a modifier on its own); when Tab, a screen
reader or code moved it after a key; and always in a text input.
`onFocusVisibleChange` fires whenever it changes, with
`event.focusVisible`, and a [`Pressable`](/docs/primitives/pressable)'s
state has it. Draw the ring with an
[outline](/docs/primitives/style#outline), which takes no room, so nothing
moves when it shows:

```tsx
const [ring, setRing] = useState(false);

<View
  focusable
  onFocusVisibleChange={(event) => setRing(event.focusVisible)}
  style={{
    borderRadius: 42,
    outlineWidth: ring ? 2 : 0,
    outlineOffset: 2,
    outlineColor: '#9473ca',
  }}
/>;
```

Both runtimes decide it by these rules, the web runtime too, rather than
by the browser's own.

## Coordinates

Layout and view-relative positions use the view's logical pixels. Screen
positions use the editor's logical pixels:

| Space   | Relative to                          | Where                                                        |
| ------- | ------------------------------------ | ------------------------------------------------------------ |
| Local   | The event's target                   | `event.locationX`, `event.locationY`                         |
| Parent  | The parent's box (scrolling aside)   | `node.layout`                                                |
| Surface | The plugin view's top-left corner    | `event.pageX`, `event.pageY`, `node.getBoundingClientRect()` |
| Screen  | The screen, in editor logical pixels | `event.screenX`, `event.screenY`                             |

`getBoundingClientRect()` is where the node shows, after its ancestors have
scrolled. Device pixels (a Retina scale, a host that zooms
the view) are the renderer's business and never show up in these numbers.
Screen positions remain stable as the editor resizes or zooms: use their
deltas for an editor resize grip. A wheel event falls back to `clientX`/`clientY`.
(`clientX`/`clientY` and `offsetX`/`offsetY` are the Web names for
`pageX`/`pageY` and `locationX`/`locationY`.)

## Pointer lock

<Snippet name="pointer-lock" height={180} />

A knob or a fader can lock the pointer while it is dragged:
`event.currentTarget.requestPointerLock()` in `onPointerDown`. While locked,
the pointer is hidden and the screen's edges don't stop it; the events keep
going to the node that locked it, their positions stay where the lock began,
and `movementX`/`movementY` say how far it moved. The lock ends with the
release, or `exitPointerLock()` from `soundor:ui`, and the pointer shows
again where it began, on the knob.

```tsx
import { View } from '@soundor/react';
import { useRef } from 'react';

function Knob({
  value,
  onChange,
}: {
  value: number;
  onChange(v: number): void;
}) {
  const dragging = useRef(false);
  return (
    <View
      style={{ cursor: 'ns-resize' }}
      onPointerDown={(event) => {
        dragging.current = true;
        event.currentTarget?.requestPointerLock().catch(() => {});
      }}
      onPointerMove={(event) => {
        if (dragging.current) onChange(value - event.movementY / 200);
      }}
      onPointerUp={() => (dragging.current = false)}
      onPointerCancel={() => (dragging.current = false)}
    />
  );
}
```

- **Only for a press:** a lock needs a mouse or pen pressing the node (or a
  node in it), which is why it is asked for in `onPointerDown`. Otherwise
  `requestPointerLock()` rejects with a `NotAllowedError`; touches are never
  locked.
- **Keep your own drag state,** as above: `movementY` works without the lock
  too, so a knob still turns if the lock is refused, stopping at the screen's
  edge.
- **`pointerLockNode()`** is the node holding the lock, or `null`. The
  release still comes under the lock, which ends after it.
- **In a browser** (the [web runtime](/docs/web-runtime)) the lock is the
  page's Pointer Lock: Escape ends it early, and Firefox says so in a banner.
